# FactLang 0.1.4 — Databricks/Spark inline timestamps carry UTC

Status: APPROVED by owner 2026-11-26 · Process: Elephant-Goldfish · Base: `main` at 0.1.3 (`83d5c54`).

## Defect
0.1.3 (§3.2 I1 of `2026-11-25-factlang-0.1.3-design.md`) inlines timestamps on `databricks` (native) and `spark`, `spark2` (bridge) as a zone-less `TIMESTAMP 'YYYY-MM-DD HH:MM:SS[.ffffff]'`. On these engines `TIMESTAMP` is session-time-zone-local by default (`spark.sql.session.timeZone`), so a zone-less literal names a different instant than the UTC value under a non-UTC session. 0.1.2's offset form did not have this defect. Reported by the downstream consumer; bound-parameter SQL is unaffected.

## Change (inline/display path only)
- `databricks`, `spark`, `spark2`: inline `TIMESTAMP 'YYYY-MM-DD HH:MM:SS[.ffffff] UTC'` — same rule as trino (space separator, explicit `UTC`, fractional seconds only when non-zero; input converted to UTC first).
- Unchanged: `hive`, `teradata`, `exasol` keep the zone-less form because their `TIMESTAMP` is a zone-less (local date-time) type, so a naive UTC wall-clock is the correct value there. Document this per-dialect reasoning next to `BRIDGE_LITERAL_STYLES` and in `docs/guide/evidence.md`.
- Verification: `sqlglot.parse_one(..., read=d)` for each changed dialect parses the literal as a timestamp whose text keeps the `UTC` zone; round-trip regeneration keeps it; bound SQL fixture unchanged (no fixture edits allowed).
- CHANGELOG `[0.1.4]` "Fixed (inline output)": names the three dialects, old and new spelling, and the session-zone reason.

## Release
Version `0.1.4`; owner pushes `release-0.1.4` and the tag (agent pushes are blocked); the tag-matrix gate publishes.

## Rule recorded for future inline changes
For every dialect, state whether its `TIMESTAMP` type is zone-aware/session-local or zone-less before choosing a spelling; zone-aware/session-local ⇒ explicit UTC zone; zone-less ⇒ naive UTC.
