    Don’t trust claims about your data. Measure them.

    FactLang is a small language for facts about data: joins, nulls, counts, allowed values, freshness. Each line comes back as a verdict; the ones that measure data run as read-only SQL over every matching row, with the numbers and the exact query as evidence.

    The idea

    Prose cannot be checked. Claims can.

    AI agents and analysts answer questions about data in prose. A wrong sentence looks exactly like a right one, so it survives, and every answer built on it is quietly wrong. FactLang turns each factual sentence into one line that a machine can measure.

    The answer said

    • “There are 1,400 paid orders.”
    • “Every order belongs to a customer.”
    • “An order’s status is paid, open or shipped.”

    As FactLang claims

    COUNT orders VALUE ==1400 WHERE status = 'paid'
JOIN orders.customer_id -> customers.id MATCH ==100%
VALUES orders.status IN ['paid', 'open', 'shipped']

    What the data says

    • pass value 1400 == 1400
    • fail match_rate 0.9765625 != 1
    • fail undeclared_rows 200 != 0, the most common being refunded
    Who it is for

    For everyone who has to trust a number about data

    AI agents & LLM apps

    Ground every answer in the data

    The agent writes the facts in its answer as claims and FactLang measures them. 3 tools (check, lint, explain) come as JSON-schema tool specs, and factlang mcp serves them over MCP. A per-call claim cap (200 by default) bounds the work; explain shows the SQL without running it.

    Data & analytics engineers

    Assumptions as plain, checkable lines

    Keep what your pipelines assume in a .fl file next to the code. factlang check exits 1 when a claim fails, 3 when one has no data or could not be measured and 2 when the file is invalid, so CI catches it. Aggregate claims over the same table and filter share one scan.

    Review & audit

    Evidence, not assurances

    Every measured verdict carries the exact SQL, its bind parameters, the dialect and its tier, and the numbers it was decided on. A claim that cannot be decided says so instead of guessing:

    no_data error unprobeable Evidence → Verdicts →
    Out of the box

    What comes with FactLang

    Each card opens the guide page that explains it in full.

    19 standard verbs

    Joins, keys, nulls, allowed values, ranges, patterns, freshness, types, counts and aggregates, each a one-line claim.

    UNIQUE orders.id

    11 native dialects

    6 are run against a real engine in CI, 5 more are checked by parsing and golden tests, and the optional sqlglot bridge covers the long tail.

    dialect="snowflake"

    Read-only by construction

    Every measured claim compiles to one SELECT. Each literal travels as a typed bind parameter, so no claim can carry SQL, and the exact statement is the evidence.

    WHERE status = ? ('paid',)

    Batching and fusion

    Check a whole file at once. The same fact is measured once however it is spelled, and aggregate claims over the same table and filter share one scan.

    Checker(connector, fuse=True)

    Diagnostics with fixes

    Stable codes, a caret under the problem and a “did you mean” when there is one. factlang lint and factlang fmt need no warehouse.

    error[FL300]: unknown verb UNIQE

    Extensible

    Add your own verbs, packs, value types, dialects, connectors and IR primitives. Each has its own guide.

    pack.register(contract)
    Under the hood

    How a claim becomes a verdict

    One claim about the Getting started shop, followed through every stage. Each artefact below is the library’s real output.

    The claim COUNT orders VALUE ==1400 WHERE status = 'paid'
    1. 1

      Parse

      The line becomes a syntax tree, with one canonical spelling.

      COUNT orders VALUE == 1400 WHERE status = 'paid'
    2. 2

      Analyse

      Names are checked against the catalog, literals are typed, and the claim gets a semantic hash: the same fact, spelled differently, hashes the same.

      sha256:d67e352999849cb4…
    3. 3

      Plan

      The verb’s contract says what to measure; the result is a small plan, which batching can fuse with others.

      ColumnAggregate(orders, ROW_COUNT, WHERE status = p1)
    4. 4

      Compile

      The plan is printed as SQL for the target dialect, here DuckDB (tier verified). The literal leaves the SQL text as a bind parameter.

      SELECT COUNT(*) AS row_count FROM orders WHERE status = ? ('paid',)
    5. 5

      Run

      One read-only query, over every row that matches the filter.

      row_count 1400
    6. 6

      Judge

      The contract derives its facts and decides. The verdict names the numbers it was decided on.

      pass · value 1400 == 1400

    Quick start

    From install to verdicts in three steps¶

    The shop from Getting started, in an in-memory DuckDB database: no warehouse needed.

    1

    Install¶

    The core has no dependencies; the duckdb extra adds the database this example uses.

    pip install "factlang[duckdb]"

    2

    Build a shop to check¶

    500 customers and 2,000 orders, with a few things wrong on purpose.

    import duckdb
import factlang as fl

conn = duckdb.connect()
conn.execute("""
    CREATE TABLE customers AS
    SELECT i AS id,
           CASE WHEN i % 25 = 0 THEN NULL ELSE 'customer' || i || '@example.com' END AS email
    FROM range(1, 501) AS t(i)
""")
conn.execute("""
    CREATE TABLE orders AS
    SELECT i AS id,
           CASE WHEN i % 160 = 0 THEN 10000 + i ELSE 1 + (i * 7) % 500 END AS customer_id,
           CASE i % 10 WHEN 0 THEN 'refunded' WHEN 1 THEN 'open' WHEN 2 THEN 'open'
                       ELSE 'paid' END AS status,
           CAST(5 + (i * 37) % 200 AS DECIMAL(10, 2)) AS amount,
           CASE WHEN i % 10 IN (1, 2) THEN NULL
                ELSE current_date - CAST(i % 30 AS INTEGER) END AS shipped_at
    FROM range(1, 2001) AS t(i)
""")

connector = fl.DBAPIConnector(conn, "duckdb")

    3

    Check what an analyst said¶

    report = fl.Checker(connector).check("""
JOIN orders.customer_id -> customers.id CARD N:1 MATCH >=99%
NULLS customers.email RATE <=5%
VALUES orders.status IN ['paid', 'open', 'shipped']
""")
for outcome in report.outcomes:
    print(f"{outcome.verdict.value:5} {outcome.explanation}")

    fail  match_rate 0.9765625 < 0.99
pass  null_rate 0.04 <= 0.05
fail  undeclared_rows 200 != 0
